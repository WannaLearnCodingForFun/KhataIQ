# M2 — Auth and core resources

## What was built (5 lines max)
- argon2 password hashing, 15-minute HS256 access JWTs, and rotating 7-day refresh tokens stored as
  SHA-256 hashes, with whole-family revocation when a rotated token is replayed.
- Routes: login / refresh / logout / me / create user, businesses (create, list, get, update),
  accounts (masked to the last 4 digits), parser catalogue. Thin routes; logic in `khataiq/services/`.
- RFC 9457 problem+json for every error, `X-Request-ID` on every response, audit rows for every write,
  and a Redis token-bucket rate limiter (60/min general, per user or per IP).

## The 3 most important design decisions
1. **Refresh-token rotation with family revocation** (`khataiq/services/auth.py:85-120`).
   Rejected: long-lived access tokens, or refresh tokens that never change. Each refresh revokes the
   presented token and issues a new one in the same family. If an already-rotated token shows up again,
   either the user or a thief has the newer one — we can't tell which, so the whole family dies
   (`_revoke_family`, line 146). The `UPDATE … WHERE revoked_at IS NULL RETURNING` on line 95 makes two
   concurrent refreshes of the same token impossible to both win.
2. **Explicit transaction per request** (`khataiq/api/deps.py:24-38`). Rejected: a `yield` dependency
   that commits after the handler. Depending on the FastAPI version that cleanup can run after the
   response is sent, so a failed commit could follow a 201. Routes write `with c.session() as s:`, which
   commits before the response exists.
3. **404 for anything you may not see** (`khataiq/services/access.py:14-45`). Rejected: 403 for "exists
   but not yours". A 403 confirms the id exists, letting someone enumerate other tenants' ids. RLS
   handles other orgs; `visible_businesses` adds "owners see only their own".

## Things that went wrong while building
- `email-validator` rejects the reserved `.test` TLD, so every login in the tests returned 422. Test
  emails moved to `example.com`, and `LoginIn.email` became a plain string: a malformed email should
  get the same 401 as an unknown one.
- The reuse test first "passed" for the wrong reason: the test client stored the cookie under
  `testserver.local`, so the replayed token was never sent and the 401 meant "missing cookie". The
  assertions now check the problem `detail`, and the test helper uses the right cookie domain.
- SQLAlchemy 2.1 changed `Select[...]`'s type parameters; mypy caught it and the dependency was pinned
  to `>=2.1`.
- Services first imported `CurrentUser` from the API package (a layering inversion). It became
  `khataiq/principal.py` so workers can call services without importing FastAPI.

## Interview questions
1. **Why short-lived access tokens plus refresh tokens?** A stolen access token works for 15 minutes at
   most and needs no DB lookup per request. The refresh token is long-lived but httpOnly (no JS access),
   only sent to `/v1/auth`, stored hashed, and rotated on every use, so theft is detectable.
2. **How do you detect a stolen refresh token?** Rotation: each use invalidates it. If an invalidated
   token is presented again, two parties had it. Revoke the whole family; both must log in again.
3. **Why store a SHA-256 of the refresh token but argon2 of the password?** Passwords are low-entropy,
   so the hash must be slow to resist guessing. A refresh token is 256 random bits; brute force is
   infeasible either way, so a fast hash is enough and keeps lookups cheap.
4. **What's the `alg: none` attack?** A JWT that says "no signature" — if the server lets the token pick
   the algorithm, it accepts anything. We pass `algorithms=["HS256"]`; a unit test proves `none` fails.
5. **Your rate limiter's Redis goes down. What happens?** It fails open and logs a warning. Rate limiting
   protects capacity; turning a limiter outage into a full API outage would be worse.
