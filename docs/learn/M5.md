# M5 — Evidence engine

## What was built (5 lines max)
- Five deterministic, versioned rules in `khataiq/evidence/`: SELF_TRANSFER (with the new *inferred*
  level), REVERSAL, DUPLICATE, LOAN_DISBURSAL and CYCLE. All pure functions over a business's ledger.
- Cycle detection: per 30-day window, iterative Tarjan SCC, then bounded (≤ 4 hops, ≤ 50) cycle search.
- `services/evidence.py` runs every rule per business as a pipeline stage, stores links under a new
  `evidence_runs` row and opens deduplicated flags; officers list, inspect and resolve flags via `/v1/flags`.
- Two schema additions, both documented in `docs/architecture.md`: `upload_rows` and `evidence_runs`.

## The 3 most important design decisions
1. **The ledger follows reconciled *statements*, not first-inserting uploads** (`services/evidence.py:40-66`,
   migration `0005`). Rejected: "transactions whose `upload_id` is reconciled". A row shared by two
   statements is stored once under whichever came first; if that statement failed reconciliation and
   the user uploaded a corrected one, the rows would stay excluded forever.
   `test_rows_from_an_unreconciled_statement_stay_out_until_a_good_one_arrives` proves the fix.
2. **SCCs before cycle search** (`evidence/graph.py`). Rejected: DFS for cycles over the whole graph.
   Every cycle lives inside one strongly connected component, and Tarjan finds them all in O(V+E); the
   expensive search then runs only inside small components, with a depth bound (4) and an output cap
   (50). Each cycle is found once by rooting it at its lowest-ordered node, the idea behind Johnson's
   algorithm. Iterative, so a 50,000-node chain doesn't hit Python's recursion limit.
3. **Uncertainty is explicit, never guessed** (`evidence/reversal.py:48`, `evidence/self_transfer.py`).
   When a reversal has two candidate debits — or one debit is claimed by two reversal credits — every
   pair is `unresolved` and goes to a human. Only uniquely-provable pairs are `verified`, so one debit
   can never back two exclusions.

## Concepts used

- Johnson's algorithm for simple cycles: https://www.cs.tufts.edu/comp/150GA/homeworks/hw1/Johnson%2075.PDF

## Things that went wrong while building
- Using the highest `run_id` in `evidence_links` as "the current run" would silently show stale links
  after a run that found nothing. Runs got their own table (`evidence_runs`), and a test covers it.
- The first ledger query trusted `transactions.upload_id` (see decision 1).
- A unit test gave every row the same default amount, so the matcher (correctly) paired rows the test
  expected to be unmatched. Lesson: test data must be built for the rule under test.

## Interview questions
1. **How do you find circular money flows in a payments graph?** Build a directed graph per time
   window, find strongly connected components with Tarjan (linear time), and only search for cycles
   inside non-trivial components, with a depth bound and a cap on results.
2. **Why iterative Tarjan?** Recursive Tarjan recurses once per node on a long path; CPython's default
   limit is 1000 frames. An explicit stack of `(node, next-neighbour index)` frames has no such limit.
3. **How do you avoid reporting the same cycle many times?** Root each cycle at its lowest-ordered node
   and only extend paths through higher-ordered nodes; across overlapping windows, dedupe by the set of
   transaction ids; across runs, flag identity = rule + version + sorted txn ids.
4. **Why are evidence rules deterministic instead of a model's probability?** An officer must be able
   to ask "why was this excluded?" and get a rule, its version and the exact rows. Re-running gives
   the same answer, and changing a rule bumps its version, so old results stay explainable.
5. **What does `unresolved` buy you over picking the most likely match?** Honesty about uncertainty: a
   wrong automatic match changes the income figure invisibly; an unresolved pair is shown as a band
   and reviewed by a human.
