# M11 — Production readiness

## What was built (5 lines max)
- Observability: structlog JSON logs with a masking processor, Prometheus metrics (HTTP latency, stage
  duration and failures, outbox depth, dead letters), OpenTelemetry spans, `/healthz` vs `/readyz`, and a
  Grafana dashboard.
- A Locust load test (officers reading, owners uploading) with measured results in `docs/results/load.md`.
- Docker images, `docker-compose.prod.yml`, `scripts/demo.sh`, and CI that runs integration tests, e2e,
  `pip-audit`/`npm audit`, an image build, and the demo stack end to end. Plus the README and demo script.

## The 3 most important design decisions
1. **Masking happens in the logging pipeline, not at each call site** (`khataiq/observability.py`,
   `mask_processor`). Rejected: relying on every developer to remember. Keys like `narration`, `password`
   and `token` are always redacted, and any 8–18 digit run keeps only its last 4 digits, so an account
   number that sneaks into a message is still masked. Tests assert that a full account number never
   appears in the output.
2. **Cross-tenant monitoring through one narrow SECURITY DEFINER function** (`alembic/versions/0009_*`).
   Queue depth and dead letters are system-wide facts, but the app role sees one tenant at a time.
   Rejected: a second, privileged DB role for `/metrics`, which would be a role that can read every
   tenant's rows. `ops_counts()` returns exactly two integers and nothing else.
3. **Liveness and readiness are different questions** (`khataiq/api/routes/ops.py`). `/healthz` says the
   process is alive and touches no dependency; `/readyz` checks Postgres and Redis. If liveness checked
   the database, one database blip would make the orchestrator restart every healthy API container at
   once.

## Things that went wrong while building
- `output: "standalone"` makes `next start` unsupported, so the e2e script now runs the standalone
  server. Orphaned `next-server` processes (node renames itself) kept port 3000 busy between runs.
  Every service now starts in its own process group (`setsid`) and is killed as a group, and the script
  refuses to start if a port is already taken.
- The e2e test passed locally but failed in CI with `net::ERR_ABORTED`: after "Sign out" the app
  redirects to `/login` itself, and the test's own `goto("/login")` raced that redirect. The test now
  waits for the redirect.
- The first screenshots were unreadable: an evidence graph with hundreds of nodes, flag summaries in raw
  paise, and a chart captured mid-animation. Fixes: a top-20 counterparty view, `inr()` formatting, and
  chart animation turned off.
- The load test's data line said "≈ 1,100 transactions". The loader actually creates 578. Fixed after
  re-counting in the database: numbers on a results page must be measured, not remembered.

## Interview questions
1. **How do you make sure account numbers never reach the logs?** A processor in the logging pipeline
   masks every event before it's written: known sensitive keys are redacted and long digit runs keep only
   their last 4 digits. It's tested with an event that contains a full account number.
2. **What's the difference between `/healthz` and `/readyz`?** Liveness means "restart me if this fails",
   so it must not depend on anything external. Readiness means "don't send me traffic right now", and
   that's where dependency checks go.
3. **Your p95 is 130 ms but p99 is 790 ms. What do you look at?** Which endpoints own the tail (here the
   graph and uploads), whether the load generator shared the CPU (it did), and the connection pool and
   worker counts. Then re-run with the generator on a separate machine before optimising.
4. **Why put Prometheus labels on the route template?** `/businesses/{id}` gives one time series;
   `/businesses/123` gives one per business, and that unbounded cardinality can take Prometheus down.
5. **What does your CI prove before a merge?** Lint and strict types; unit and integration tests against
   real Postgres and Redis on three Python versions; migrations match the models; frontend types match
   the API's OpenAPI; a browser test through the whole stack; no known-vulnerable dependencies; the
   images build, start, seed and serve.
