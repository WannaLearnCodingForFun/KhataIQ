# M4 — Pipeline

## What was built (5 lines max)
- The outbox relay (`khataiq/pipeline/outbox.py`): claims rows with `FOR UPDATE SKIP LOCKED` through two
  narrow SECURITY DEFINER functions, publishes, marks them published — at-least-once, never zero.
- A broker-agnostic stage runner (`runner.py`): attempt records, idempotent skips, retries after
  2/4/8/16 s, dead after 5 attempts, permanent errors fail fast. Celery wiring in `celery_app.py`.
- Stages parse → persist → reconcile (`stages.py`), with the reconciliation gate opening a flag.
- Admin dead-letter list/retry and audit search; a test that runs a real Celery worker against Redis.

## The 3 most important design decisions
1. **Idempotent stages + at-least-once delivery** (`runner.py:135-192`, `stages.py:65-83`).
   Rejected: trying for exactly-once delivery (impossible across a broker and a DB). Instead every
   message may arrive more than once and nothing breaks: an attempt row is
   `UNIQUE(upload_id, stage, attempt_no)`, a stage that already succeeded is skipped (but re-dispatches
   its successor, which heals a chain broken by a crash between commit and dispatch — line 163), and
   persist uses `ON CONFLICT DO NOTHING`. The test `test_running_the_chain_twice_leaves_identical_state`
   hashes every ledger table before and after.
2. **Stage effects and the success mark in one transaction** (`runner.py:167-174`). If the commit
   fails, the attempt isn't marked succeeded, so it's retried — and the retry is safe because of (1).
3. **Permanent vs transient errors** (`runner.py:175-189`). A `ParseError` will fail the same way every
   time, so retrying it five times only delays the user seeing "line 5: not a date". It fails at once.
   Everything else (storage timeouts, deadlocks) is assumed transient and retried with exponential
   backoff, then parked as `dead` for an admin.

## Things that went wrong while building
- `Result.tuples()` is deprecated in SQLAlchemy 2.1 and returned an object that couldn't be turned into a
  dict; `.all()` returns rows that unpack directly.
- Writing the interview answer about worker crashes exposed a real bug: a redelivered message found
  its own `running` attempt row and skipped, leaving the stage stuck forever. Now a `running` attempt is
  taken over, serialized by the upload row lock (`runner.py`, `_run`), with a regression test.
- A test expected a parse error on line 4; it was line 5 because the first day has two rows. The code
  was right; the test's arithmetic was wrong.
- The VPA regex swallowed `KIRANA-` from `UPI-RAMESH KIRANA-ramesh@okicici`; `-` was removed from the
  local-part character class (trade-off documented in `enrich.py`).

## Interview questions
1. **Two relay processes run at once. Why doesn't a job get published twice?** Each claims rows with
   `FOR UPDATE SKIP LOCKED` inside its transaction; the other skips locked rows instead of waiting.
   A crash after publishing but before commit can re-publish a row later — that's why consumers are idempotent.
2. **What happens if a worker dies halfway through a stage?** Its work transaction never commits, so
   nothing it did is visible. With `acks_late` the broker redelivers the message. The redelivery finds
   the attempt row still `running` and takes it over; the upload row lock plus a re-check of "already
   succeeded?" means even a live duplicate can only run the stage after the first finishes, and then
   finds nothing to do. (Follow-up: if the *message* is lost too, a reaper for runs stuck in `running`.)
3. **Why not pass the parsed rows from parse to persist in the message?** Messages should be small and
   brokers aren't databases. Each stage re-reads the file and re-parses; parsers are pure and
   deterministic, so they see identical rows.
4. **How do you make a pipeline stage idempotent?** Make its writes conditional on state
   (`ON CONFLICT DO NOTHING`, `WHERE revoked_at IS NULL`), keep its effects and its "done" mark in one
   transaction, and record attempts under a unique key so duplicate deliveries are no-ops.
5. **Why does reconciliation stop the pipeline instead of just warning?** Every later number (evidence,
   metrics) assumes the ledger is complete and correct. A statement that doesn't add up is missing or
   altered rows; computing cash flow from it would present wrong numbers with false confidence.
