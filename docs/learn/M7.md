# M7 — Synthetic data and evaluation

## What was built (5 lines max)
- `synthetic/generator.py`: a seeded, byte-for-byte deterministic generator of businesses (1–3 accounts,
  6 months of demo-bank statements) with planted self-transfers, ambiguous transfers, reversals,
  overlapping statements, near-duplicates, circular flows and a loan, plus a ground-truth file.
- `synthetic/evaluate.py`: runs the real pipeline in-process on N businesses and scores every rule.
- `docs/results/evidence_eval.md` (200 businesses, ~116k transactions) and a 6-business run in CI.

## The 3 most important design decisions
1. **The evaluation runs the real pipeline, not the rules in isolation** (`synthetic/evaluate.py`,
   `process`). Uploads go through `create_upload`, the outbox, every stage and the database, so the
   evaluation also tests ordering effects between uploads. That's how it found the stale-flag bug
   (decision 3) — the rules alone were fine.
2. **Unresolved is neither a hit nor a false positive** (`_score_business`). The engine is designed to
   hand ambiguity to a human; counting `unresolved` as a miss would push the rules toward guessing,
   counting it as a hit would hide uncertainty. It's reported in its own column.
3. **Fix the rules, not the data.** The first 40-business run showed CYCLE precision 0.34. Three real
   causes, all fixed in the engine: flags raised before the other account's statement arrived were never
   closed (now superseded, and reopened if the finding returns); the same flow seen from overlapping
   windows made several flags (identity is now the counterparty legs); and the 50-cycle cap counted
   cycles that could never be reported, crowding out real ones (the cap now applies to reported cycles,
   with a separate search budget). Two remaining misses are documented, not hidden.

## Concepts used
- Precision and recall: https://en.wikipedia.org/wiki/Precision_and_recall
- Seeded pseudo-random generators (`random.Random`): https://docs.python.org/3/library/random.html#random.Random
- Ground truth / synthetic test data for pipelines: https://en.wikipedia.org/wiki/Synthetic_data
- Regression tests that fail on the old code: write the test, revert the fix, watch it fail.

## Things that went wrong while building
- CYCLE precision 0.34 on the first run — see decision 3. Each cause was confirmed by querying the
  evaluation database before changing code.
- The first "cap" regression test didn't reproduce the bug (two accounts make only one internal loop). It
  was rewritten and checked by restoring the old budget and watching it fail.
- Reopening superseded flags looked like the cause of the remaining misses but wasn't; a debug hook
  printing each missed flow and its flags found the real causes (an evaluation criterion that ignored
  that a cycle's identity is its counterparty legs, and the cap).

## Interview questions
1. **How do you evaluate a system when you have no labelled real data?** Generate data with known
   answers (planted events), run the real pipeline end to end, and score against the plant. Be explicit
   that this proves the pipeline finds what was planted, not real-world accuracy.
2. **What's the danger of synthetic evaluation?** The same person wrote the generator and the rules, so
   the data shares the rules' assumptions. Perfect scores are expected and say little; the value is in
   regressions and in the failure modes it exposes.
3. **Why must the generator be deterministic?** So a score change means the code changed, not the data,
   and any miss can be reproduced from its seed.
4. **Your rule had 0.34 precision. What did you do?** Looked at the actual false positives in the DB,
   grouped them by cause, fixed each cause in the engine with a regression test, and re-ran.
5. **Why is "unresolved" reported separately?** It's the designed outcome for ambiguity; folding it into
   precision or recall would reward guessing or hide uncertainty.

## Try it yourself (15 minutes)
Add a planted event: "cash deposit followed by a same-day transfer out of the same amount". Record it in
ground truth, run `python -m synthetic.evaluate --n 20`, and look at what (if anything) the engine says.
