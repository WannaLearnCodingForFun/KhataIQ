# M8 — Machine learning (supporting, never authoritative)

## What was built (5 lines max)
- `classify/rules.py`: an ordered, versioned rule table (first match wins), labelling ~12% of rows.
- `classify/model.py` + `synthetic/train_label_model.py`: TF-IDF (char 2–5) + logistic regression for
  the rest, confidence floor 0.6 → `other`; a classify pipeline stage. Macro-F1 0.534 rules-only →
  0.831 rules + model on held-out businesses; 0.837 on the 200 evaluation businesses.
- `experiments/forecast/`: rolling-origin LightGBM vs last-value and seasonal-naive, tracked in MLflow.
- `experiments/risk_benchmark/`: Home Credit pipeline with leakage checks, calibration and SHAP (not run
  here: the data needs a Kaggle account).

## The 3 most important design decisions
1. **Split by business, never by row** (`synthetic/train_label_model.py`). Rows of one business share
   names, VPAs and habits; a row-level split would put near-copies of test rows in training and inflate
   the score. Even so, the generator's name pools are shared across businesses, which the results page
   says out loud.
2. **Rules first, the model only for what rules miss, humans always win** (`pipeline/stage_classify.py`,
   the `current_txn_labels` view). Rules are explainable and versioned; the model fills gaps with a
   confidence; a human label overrides both. A low-confidence prediction becomes `other` rather than a
   guess. Labels feed evidence (loan disbursals) but never decide an evidence level on their own.
3. **"Beats the baseline" is necessary, not sufficient** (`docs/results/forecast.md`). LightGBM beat
   seasonal-naive by 18–22% at 1–2 months and 0.2% at 3 months — on synthetic data. The app shows no
   forecast until it's repeated on real histories. Likewise the risk benchmark's page says what
   population it is and why it can't score KhataIQ businesses.

## Things that went wrong while building
- MLflow's file store is in maintenance mode in current releases and refused to start; the experiment
  uses the SQLite store, and telemetry is turned off (the sandbox blocks it anyway).
- The first forecast origin had no training data: the 12-month lag needs a year of history before any
  target can be used. Training now starts at the first month whose lag exists, and origins at month 14.
- pandas 3 gives strings their own dtype instead of `object`, so the risk script's categorical check
  silently treated text as numeric; it now asks "is this numeric?" instead.
- The training script first lived in `khataiq/classify/`, importing the `synthetic` package; production
  code mustn't depend on test tooling, so it moved to `synthetic/`.

## Interview questions
1. **Why is macro-F1 the headline metric for labels?** 64% of rows are sales; accuracy and weighted F1
   are dominated by that class. Macro-F1 weights every label equally, so a model that ignores `rent`
   can't hide.
2. **How do you avoid leakage in a time-series forecast evaluation?** Rolling origin: at each origin,
   train only on targets already observed, compute features only from data up to the origin, and
   score the next h months. Never shuffle time.
3. **Your model beats the baseline. Do you ship it?** Not on its own: check the margin per horizon
   (0.2% is noise), whether the evaluation data resembles production (here it doesn't — it's synthetic),
   and whether the error band can be shown honestly.
4. **What does a calibration curve tell you that ROC-AUC doesn't?** AUC measures ranking; calibration
   measures whether "20% risk" really means 20% of such cases default. For decisions that use the
   probability itself (pricing, limits), calibration matters more.
5. **Why can't a Home Credit model score Indian small businesses?** Different population, different
   features, different outcome. Performance only transfers to data like the training data; validating it
   would need repayment outcomes for small businesses whose statements were analysed before the loan.

## Try it yourself (15 minutes)
Add a rule `RENT_LANDLORD` that labels a debit as `rent` when the same person-name counterparty is paid
on the same day of the month for 3+ consecutive months (you'll need more than one row — think about
where that logic belongs). Re-run `python -m synthetic.train_label_model` and compare rent F1.
