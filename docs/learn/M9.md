# M9 — Copilot

## What was built (5 lines max)
- `copilot/tools.py`: five typed, read-only tools (metrics, transactions, flags, evidence, uploads),
  scoped by RLS to the org and by the server to one business; each records the rows it returned.
- `copilot/grounding.py`: a pure checker — cited ids must come from this turn's tool results, and every
  ₹ figure must equal a cited value or a signed sum of up to 3 *different* cited values.
- `copilot/service.py`: the tool loop (≤ 6 tool calls), one corrective retry, then a fixed decline;
  `POST /v1/businesses/{id}/copilot` (officers, 20/hour), conversations stored in `copilot_messages`.

## The 3 most important design decisions
1. **The server checks the model's arithmetic, not the model** (`copilot/grounding.py`). Rejected:
   trusting citations, or asking the model to "only use real numbers". The checker knows exactly which
   rows the tools returned in this turn, so an invented transaction id or an invented ₹ figure is
   caught deterministically. The model gets one chance to fix it with the precise failure; then the
   officer gets "I couldn't answer that" instead of a confident wrong number.
2. **The model never chooses the tenant or the business** (`copilot/tools.py`, `ToolContext`). Tools
   take filters only; the business id and the tenant session are injected by the server. Even a
   prompt-injected request can't read another business, and RLS backs that up.
3. **A thin `LLMClient` interface** (`copilot/llm.py`). The loop depends on `chat(...) -> LLMResponse`,
   not the SDK, so tests drive it with a scripted fake that reads the real tool results — every path
   (clean, made-up id, made-up figure, retry fixes it, tool cap, refusal, follow-up) is tested
   without network or cost. The Anthropic implementation uses structured outputs for the JSON answer,
   explicit effort, and server-side refusal fallbacks.

## Things that went wrong while building
- The first sum check used `combinations_with_replacement`, so one cited ₹25,000 "proved" ₹50,000. A
  test caught it; the check now uses each cited value at most once.
- A test's own arithmetic was wrong (₹1,32,845.50 instead of ₹1,27,345.50) — the checker was right.
- The SDK's typed overloads rejected plain dicts for tools and `output_config`; those arguments are now
  passed as `Any` with a comment, instead of scattering `type: ignore`.
- Not verified against the live API: this environment has no API key. The fake covers the loop; the
  first real call should be watched for schema rejections of the tool definitions.

## Interview questions
1. **How do you stop an LLM from inventing numbers?** Don't ask nicely — verify. Log which rows each
   tool returned this turn; require citations; check every figure against the cited rows (allowing
   small sums/differences); retry once with the exact failure; otherwise decline.
2. **Why only one retry?** Each retry costs latency and money and rarely succeeds after the second
   failure; a clear "couldn't answer" is better UX than a slow wrong one, and failures are logged.
3. **How is the copilot tenant-safe?** Authorization isn't the model's job: the route requires an
   officer, the tools run in that officer's RLS-scoped session, and the business id is injected
   server-side. A malicious prompt can only make the model call the same read-only tools.
4. **How do you test LLM code without calling the LLM?** Put the provider behind a small interface and
   drive the loop with a scripted fake; keep the checking logic pure so it can be unit-tested
   exhaustively.
5. **Why cap tool calls?** Bounded cost and latency per question, and a guard against loops; when the
   cap is hit the model is told to answer with what it has.

## Try it yourself (15 minutes)
Add a tool `get_top_counterparties(direction, limit≤10)` returning the counterparties with the largest

"Who are the biggest customers?" and passes grounding.
