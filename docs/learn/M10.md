# M10 — Frontend

## What was built (5 lines max)
- A Next.js 15 (App Router, TypeScript strict, Tailwind) app in `frontend/` with typed API access generated
  from FastAPI's OpenAPI (`openapi-typescript` + `openapi-fetch`).
- Owner pages: businesses, accounts, drag-and-drop upload with live stage progress and the exact
  reconciliation break. Officer pages: overview chart with the uncertain band, virtualised transactions
  with relabelling, evidence graph (Cytoscape), review queue, assessment state machine, copilot panel.
- Admin page: dead letters with retry, audit search. A Playwright smoke test over the whole stack.

## The 3 most important design decisions
1. **Access token in memory, refresh token in an httpOnly cookie** (`src/lib/api.ts`). Rejected:
   `localStorage`, where any XSS can read a long-lived credential. On a page reload the memory is empty, so
   `AuthProvider` asks `/v1/auth/refresh`; a 401 mid-session refreshes once (concurrent 401s share one
   refresh) and retries, else the user is sent to `/login`.
2. **Same-origin API through Next rewrites** (`next.config.ts`). The browser calls `/v1/...` on the
   frontend's origin, which proxies to the API. The refresh cookie (`Path=/v1/auth`, `SameSite=Strict`) is
   then first-party, and no CORS credentials setup is needed.
3. **No hand-written API types** (`npm run gen:api`). Types come from `openapi.json`, exported from the
   running FastAPI app (`scripts/export_openapi.py`). Renaming a field in a Pydantic schema breaks
   `tsc` in the frontend instead of breaking a page at runtime.

## Things that went wrong while building
- The pinned `next@15.5.4` carried a published security advisory; moved to the patched 15.5.x. Transitive
  `postcss` and `sharp` advisories were fixed with npm `overrides` instead of jumping to Next 16, which the
  spec doesn't allow; image optimisation is off because the app doesn't use it.
- The smoke test caught a real bug: after an upload finished, the overview still showed its cached "no
  statements yet". The upload page now invalidates metrics, uploads, transactions and flags when the
  pipeline reaches a final state.
- A `pkill -f "uvicorn khataiq"` used while debugging matched its own shell and killed it — use PIDs.

## Interview questions
1. **Where do you keep the access token in a SPA, and why?** In memory: short-lived and unreadable after
   the tab closes. The long-lived refresh token is in an httpOnly, Secure, SameSite=Strict cookie scoped to
   the refresh path, so JavaScript (and an XSS) can't read it and other sites can't send it.
2. **Two requests get a 401 at the same time. What happens?** Both await one shared refresh promise, then
   retry with the new token. Without sharing, two refreshes would race and the second would present an
   already-rotated token — which the backend treats as theft and revokes the family.
3. **How do you keep frontend and backend types in sync?** Generate them from the OpenAPI document the
   backend produces; the typecheck fails when they drift.
4. **How does the upload page know the pipeline finished?** It polls `GET /uploads/{id}` every 2 s until a
   final status, then stops polling and invalidates every query derived from the ledger.
5. **Why virtualise the transactions table?** A business can have tens of thousands of rows; rendering
   only the visible ones keeps the DOM small and scrolling smooth, with pages fetched on demand.
