# M3 — Uploads

## What was built (5 lines max)
- `khataiq/storage.py`: an S3/MinIO object store (boto3), tested against moto's in-memory S3.
- `POST /v1/accounts/{id}/uploads`: 10 MB cap enforced before parsing, CSV/PDF sniffed from the bytes,
  SHA-256 dedupe (200 for a file already uploaded), `Idempotency-Key` replay and 409 on key reuse, and
  the upload row + its outbox job written in one transaction.
- `GET /v1/uploads/{id}` (stages + reconciliation break) and `GET /v1/businesses/{id}/uploads`.

## The 3 most important design decisions
1. **Storage write first, then one DB transaction** (`khataiq/services/uploads.py:1-20, 98-128`).
   Rejected: insert the row, then upload the file. If the file write failed after the commit, a row
   would point at nothing and the pipeline would fail forever. Our order can only leave an *orphan
   object* — harmless, and sweepable by a bucket lifecycle rule. The upload id is reserved from the
   sequence first (`nextval`) so the object key can include it.
2. **Transactional outbox** (`_insert_upload`, line 160). Rejected: enqueue the Celery job straight from
   the request. If the broker call succeeded and the commit failed, a job would run for an upload that
   doesn't exist; if the commit succeeded and the broker call failed, the upload would never be
   processed. Writing the job as a row in the same transaction makes "upload exists ⇔ job exists" an
   invariant; a relay (M4) publishes it later.
3. **Two kinds of "same request"** (`_earlier_result`, line 131). An `Idempotency-Key` replay returns
   the original status (201) and upload; a different key with the same bytes is a *duplicate file* and
   returns 200 with the existing upload. The same key with different bytes is a client bug → 409.

## Things that went wrong while building
- moto only intercepts requests to AWS endpoints, so `s3_endpoint` became optional (empty = AWS) and
  tests set it empty.
- FastAPI parses the whole multipart body before any route code or dependency runs, so a 2 GB upload
  would hit disk before a size check in the route. The cap moved into ASGI middleware, which checks
  `Content-Length` and also counts streamed bytes.

## Interview questions
1. **What is the outbox pattern and what problem does it solve?** You can't atomically write to a DB
   and publish to a broker. Write the message as a row in the same transaction as the data; a relay
   publishes unpublished rows later. Worst case is a duplicate publish, which idempotent consumers absorb.
2. **How does your upload endpoint stay idempotent?** The client sends a UUID `Idempotency-Key`; we store
   `(org, key) → request hash, status, upload id` in the same transaction as the upload. A retry with the
   same key and body gets the original response; same key with a different body gets 409.
3. **Why reserve the id before writing the file?** The storage key contains the upload id, and the file
   must be stored before the row commits, so the id is taken from the sequence first.
4. **Why sniff the content type?** The filename and `Content-Type` header are client-controlled. The
   first bytes (`%PDF-`, decodable comma-separated text) are what the parser will actually see.
5. **Where would you enforce a body-size limit, and why there?** In front of body parsing: ideally at
   the reverse proxy (`client_max_body_size`) and also in ASGI middleware, before the framework spools
   the body to disk.
