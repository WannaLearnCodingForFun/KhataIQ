# M0 — Statement parsers

## What was built (5 lines max)
- `normalize.py`: exact rupee-string → paise conversion, strict date formats, 12-digit UTR extraction.
- A parser registry keyed by `(bank, format)`, plus four parsers: `demo/csv`, `demo/pdf_text`,
  and two config-driven CSV banks (`hdfc_like`, `sbi_like`) sharing one `GenericCsvParser`.
- Golden-file tests for every parser; each fixture also has to pass `core.ledger.reconcile`.

## The 3 most important design decisions
1. **Parse money as text, never float or Decimal** (`khataiq/pipeline/normalize.py:14-43`).
   Rejected: `round(float(x) * 100)` and `Decimal(x)`. `float('0.29') * 100` is
   `28.999999999999996`, and `Decimal` happily accepts `NaN`, `inf` and `1e3`. A regex with
   `fullmatch` defines exactly what a valid amount looks like, and `int()` on each part is exact.
2. **New banks are config, not code** (`khataiq/pipeline/parsers/configs.py`,
   `generic_csv.py:112`). Rejected: one parser class per bank. Columns are found by header name, so
   a bank reordering columns doesn't break us, and adding a bank is a ~15-line dataclass.
3. **Errors carry a location** (`ParseError(line_no, …)`, `csv_common.py:47-58`). Every
   `ValueError` from a value parser is re-raised as `ParseError` with the line number using
   `raise … from exc`, so the upload status can tell the user *where* the file is wrong while the
   original exception stays attached for debugging.

## Things that went wrong while building
- The hand-written SBI golden file said the NEFT row had no UTR, but `N310260098765` contains a
  12-digit run after the `N`. The spec ("12 digits not touching another digit") says the parser is
  right, so the golden file was fixed. Lesson: a golden file is only as good as your reading of the spec.
- Registering the PDF parser as `("demo", "pdf")` broke an existing test that uses that pair as its
  example of an *unknown* parser. Instead of editing the test, the format was named `pdf_text`,
  which is also more accurate (text-layer PDFs only).
- pdfplumber wraps parse failures in its own `PdfminerException`, not pdfminer's `PDFSyntaxError`.

## Interview questions
1. **Why not store money as float?** Binary floating point can't represent most decimal
   fractions exactly (0.1, 0.29), so sums drift and equality checks fail. Integer paise are exact;
   formatting to rupees happens only at the UI edge.
2. **How do you know your parser didn't change behaviour after a refactor?** Golden files: each
   fixture's full parsed output is checked in; the test compares exactly. Any change fails CI and
   must be justified (and the parser version bumped).
3. **A bank changes its CSV export. What breaks?** If they rename a column, `_column_index`
   raises `ParseError` at the header line; if they only reorder, nothing breaks because columns are
   mapped by name. Fix = config change + new fixture + version bump.
4. **Why derive the opening balance, and what's the risk?** Some exports have no opening line.
   Deriving it from row 1 means row 1 can't fail reconciliation, but every later row and the
   closing balance still must add up, so tampering is still detected from row 2 on.
5. **Why does a 16-digit card number not match the 12-digit UTR regex?** The lookbehind `(?<!\d)`
   and lookahead `(?!\d)` require the 12 digits not to touch another digit, so a longer run never
   matches part of itself.
